## Problem Statement

Build a centralized digital appointment scheduling platform for Jigme Dorji Wangchuck National Referral Hospital (JDWNRH), Bhutan, framed as a scenario/reference (not a real deployment). Patients discover services, select department/specialty/doctor, view real available slots, book/cancel/reschedule appointments, and receive confirmations and reminders. Hospital staff (nurses, receptionists) run day-to-day operations: check-in, queue management, appointment status. Doctors manage their own schedule and appointment list. Administrators manage the full system: users, departments, specialties, doctors, schedules, holidays, booking rules, and reporting. Explicitly scoped as production-grade, not a simple CRUD app. At least four major role categories, refined into seven granular roles for RBAC (see RBAC section).

## What Makes This Cool

Most student/portfolio scheduling projects claim correctness under concurrency ("no double bookings") without ever proving it. This design makes that claim a checked-in, screenshot-able artifact: a load test that fires concurrent booking requests at the same doctor-time range and shows zero double-bookings, sitting next to the DB constraint that guarantees it. That's the "whoa" — not more features, but visible proof that the hardest part of a scheduling system actually works, on top of a properly layered Spring Boot backend that reads like real hospital software, not a CRUD demo.

## RBAC — Roles and Permissions

Seven granular roles (refines the "at least four major roles" framing — Patient / clinical staff / front-of-house staff / administration, split into their real-world granularity):

```
PATIENT
 ├── Book appointment · Cancel/reschedule own appointment (per policy)
 └── View own appointments, history, profile

DOCTOR
 ├── View own schedule, assigned appointments, patient info permitted by role
 ├── Mark appointment status, indicate consultation completion
 └── Define/request availability, block unavailable periods

NURSE
 └── (subset of RECEPTIONIST + clinical visibility — check-in, queue, status updates
      for assigned department; does not manage schedules or users)

RECEPTIONIST
 ├── Manage appointments, check-in patients, search patients
 ├── Manage daily appointment queue
 └── Reschedule/cancel on a patient's behalf per policy

DEPARTMENT_ADMIN
 ├── Manage doctors, schedules, appointment types within their department
 └── Department-scoped reports

HOSPITAL_ADMIN
 ├── Manage users, departments, specialties, doctors, staff
 ├── Manage schedules, holidays, working hours, booking rules, cancellation rules
 └── View system audit logs, generate hospital-wide reports

SUPER_ADMIN
 └── Full system configuration, role/permission management
```

Staff (nurse/receptionist) do **not** automatically get administrative access — permission checks are per-action, not per-portal. Doctor access, like every other role, is enforced via RBAC at both the application layer and the database layer (see Data & Correctness Architecture).

## Tone & Emotional Arc

This is a hospital booking flow, not a shopping cart — patients are often anxious about *why* they need the appointment, not just the logistics of booking it. Confirmation and reminder copy is specific and reassuring ("Your appointment with Dr. Tshering Wangmo is confirmed for Thu, 27 Aug, 10:30am" — not "Success!" or "Booking confirmed."). If a patient can't find an available slot for weeks in a department, that's a real source of anxiety, not just friction — the empty/no-availability state (see Interaction States below) should point to a next step (e.g. "call reception" for v1; a waitlist is future work per Explicitly Out of MVP) rather than a dead end.

- **Touch targets:** 44px minimum on all interactive elements (buttons, slot cells, nav items) — the stated audience includes elderly and less tech-savvy patients, where this isn't a nice-to-have.
- **Contrast:** WCAG AA minimum (4.5:1 for body text), consistent with the wireframe's high-contrast, uncluttered brief.
- **Keyboard navigation:** the full booking flow (department → doctor → slot → confirm) must be operable by keyboard alone, including visible focus states.
- **Screen readers:** semantic headings and ARIA landmarks for the booking flow and appointment status (a status like CHECKED_IN must be announced, not conveyed by color alone).
- **Responsive, not just "stacked on mobile":** the slot grid becomes a scrollable single-column list on narrow viewports (not a squeezed grid), and primary nav collapses to a bottom tab bar on mobile rather than a hamburger menu — bottom-of-thumb reach matters more than novelty here.

## Appointment Booking Flow

```
Login/Register → Select Department/Specialty → Select Doctor → Select Appointment Type
→ Select Date → View Available Slots (backend-computed, never frontend-trusted)
→ Select Time → Confirm → Appointment Created → Confirmation + Reference Number

```

## Appointment Status Model

A controlled state machine — transitions are enforced server-side, not arbitrary status writes:

```
PENDING → CONFIRMED → CHECKED_IN → WAITING → IN_CONSULTATION → COMPLETED
```

`CANCELLED`, `NO_SHOW`, and `RESCHEDULED` are handled as separate terminal/branching transitions, not part of the happy-path chain above. Every appointment gets a unique, human-usable reference (e.g. `JDW-2026-000123`, exact format decided at implementation time) usable by patient, reception, staff, and doctor to look up the same record.

**Reschedule mechanism (explicit, since it determines the schema):** a reschedule never mutates an existing `Appointment` row's time range in place. It marks the original row `RESCHEDULED` (a terminal status, which drops it out of the partial exclusion index and frees its range) and inserts a brand-new `Appointment` row for the new time, carrying a `rescheduled_from_id` FK back to the original. **The reference number carries forward to the new row unchanged** — a patient calling in with their original confirmation's reference always resolves to the current active appointment, without staff needing to manually traverse the `rescheduled_from_id` chain (the chain still exists, for audit/history purposes, but lookup-by-reference doesn't depend on it). Both rows link into the same `AppointmentHistory` trail. This keeps the exclusion constraint's semantics simple — it only ever has to reason about one row per booking, never an in-place range update.

## Data & Correctness Architecture

This is the load-bearing part of the design — the mechanism that actually earns the "production-grade" claim.

- **Slot availability is always backend-computed.** Given a doctor's working hours, breaks/blocked periods, appointment duration, existing appointments, and hospital booking rules → available slots. The frontend is never the source of truth for availability; it only renders what the backend returns. This is stated as an explicit architectural rule specifically because it's the rule most likely to get silently violated under time pressure.
- **Double-booking prevention is a database constraint, not application logic.** Because appointment durations vary by type (e.g. 20 min standard vs. longer new-patient visits) and each slot needs buffer time, a plain unique constraint on `(doctor_id, start_time)` is insufficient — it doesn't stop two different-length appointments from overlapping the same doctor-minute at different start times. Use a Postgres exclusion constraint: `EXCLUDE USING gist` on a `tstzrange` column representing `(doctor_id, appointment_range)`, where the range already includes buffer padding (a 20-min appointment with a 5-min buffer writes a 25-min range). Slot-generation must compute availability against that same padded range so an offered slot never actually collides at write time.
- **The exclusion constraint must be partial, scoped to active/occupying statuses only** — `WHERE status IN ('PENDING','CONFIRMED','CHECKED_IN','WAITING','IN_CONSULTATION')`. Without this qualifier, a cancelled or no-show appointment's row would permanently block rebooking that doctor-time-range, which directly breaks the cancellation flow and undercounts availability. This was caught in adversarial review of an earlier draft and is a correctness requirement, not a nicety.
- **JPA/Hibernate does not express a GiST exclusion constraint via annotations.** Map the columns normally (`doctorId`, `appointmentRange` as a range type or two timestamps), but create the actual constraint via a raw-SQL Flyway migration. This is a common trap — assuming the ORM layer alone can express the guarantee — worth calling out explicitly so it isn't discovered late. That migration must also enable the extension the constraint depends on: `CREATE EXTENSION IF NOT EXISTS btree_gist;` before the `EXCLUDE` constraint, since GiST-indexing a plain equality column (`doctor_id`) requires it — the single most common trap when this pattern is used for the first time, easy to miss because the error only appears when you actually try to create the constraint.
- **Auth mechanism: JWT (stateless), short-lived, httpOnly refresh.** A stateless access token (issued at login, carrying user id + role + department id, verified by Spring Security on each request) matches the decoupled-SPA direction already implied by the Distribution Plan, and gives the request-scoped values the RLS interceptor needs without a server-side session store. **Access tokens are short-lived (~15 minutes).** The **refresh token lives in an httpOnly, Secure, SameSite cookie** — never in localStorage/JS-reachable storage, so an XSS bug can't exfiltrate it — and is checked against a **server-side revocation list** on every refresh, so logout actually invalidates the session rather than just clearing a client-side copy.
- **Role/department change is enforced immediately, not just bounded by token expiry.** The 15-minute access-token window alone would let a demoted or reassigned user keep acting under stale RLS-enforced permissions until the token expired. To close that fully: every request touching an RLS-protected table re-verifies the JWT's role/department claim against the current DB value (one indexed lookup, not a full user reload) before the RLS session variables are set — a revoked/changed role takes effect on the very next request, not up to 15 minutes later. This adds one DB read per RLS-sensitive request and gives up some of the point of pure statelessness, but for a system whose central claim is "RLS survives an app-layer bug," a bounded-but-open window undercuts that claim.
- **RBAC enforced at two layers:** application-level (Spring Security method/role checks) AND query-level (Postgres Row-Level Security scoped by session variables set per request from the JWT claims: `app.current_role`, `app.current_user_id`, and `app.current_department_id` for department-scoped roles — see next point) — RLS survives an app-layer bug, which is exactly the kind of thing a portfolio reviewer will probe for.
- **RLS only binds if the app connects as a non-owner role — this was the single most important gap caught in review.** Postgres table owners bypass RLS policies by default. Flyway migrations run as the schema-owning role (needed for DDL), but the Spring Boot application must connect as a **separate, non-owner `app_user` role** with `ALTER TABLE ... FORCE ROW LEVEL SECURITY` set on every RLS-protected table. Without this, every RLS policy in this design is dead code — it would still pass tests, because tests would default to running as the same owning role too. This is a hard requirement, not an optimization: provision `app_user` before writing the first RLS policy, and make sure both the app's runtime connection string and the test Testcontainers setup use it, not the migration/owner role.
- **Department-scoped RLS needs its own session variable.** `NURSE` and `DEPARTMENT_ADMIN` are scoped to a department, not just a role — `app.current_role` alone can't express that boundary. RLS policies for department-scoped tables (e.g. `Appointment`, `DoctorSchedule`) must also check `app.current_department_id`, set from the JWT's department claim alongside role and user id. Without this, the "RLS survives an app-layer bug" guarantee would quietly only apply to role checks, not department boundaries — which is most of what those two roles actually need enforced.
- **RLS session variables and connection pooling — simpler here than a serverless stack, but still needs care.** `SET LOCAL app.current_role = '<role>'` (and the user-id/department-id equivalents) only work reliably when set within the same transaction/connection that runs the query. A conventional Spring Boot server with a HikariCP connection pool checks out one physical connection per request/transaction, so this is naturally safe *as long as the app connects to Postgres directly* (Neon's direct connection string), not through Neon's PgBouncer-in-transaction-mode pooled endpoint, which can break `SET LOCAL` semantics across pooled connections the same way it would for a serverless stack. Wrap the RLS variable set inside a `@Transactional` boundary (e.g. a Spring interceptor/aspect that runs it as the first statement of every request transaction, reading the values from the verified JWT) — validate this end-to-end with one doctor/patient pair before building further.
- **Hibernate's second-level cache must stay disabled.** If L2 caching is left on (or enabled later for performance without thinking this through), cached entities can be served across different RLS session contexts, since Hibernate's cache has no concept of `SET LOCAL app.current_role`/`app.current_department_id`. That would quietly undermine the DB-enforced-RBAC guarantee this whole section exists to establish — explicitly leave L2 cache off, and if it's ever turned on, it must be per-user/department cache-key-scoped, not a blanket entity cache.
- **Audit log** (`AuditLog` entity) records who/what/when/resource/previous-value/new-value for: login, appointment created/cancelled/rescheduled, doctor schedule changed, patient record updated, user role changed.
- **`reference_number` is not a plain-unique column.** Because it carries forward unchanged across a reschedule (see above), a reschedule chain of length N leaves N `Appointment` rows sharing one reference number — a naive `UNIQUE` constraint on that column would reject the reschedule insert outright and silently break the feature. Enforce uniqueness with a partial unique index scoped to active statuses instead (the same pattern as the exclusion constraint), e.g. `UNIQUE (reference_number) WHERE status IN ('PENDING','CONFIRMED','CHECKED_IN','WAITING','IN_CONSULTATION')` — at most one *active* row per reference number, with historical `RESCHEDULED` rows free to share it.

## Backend Architecture

```
Frontend
   ↓
REST API
   ↓
Application Layer
   ↓
Domain Layer
   ↓
Infrastructure Layer
   ↓
PostgreSQL
```

Modules (bounded contexts, not necessarily separate deployables): IAM, Patient, Doctor, Department, Scheduling, Appointment, Notification, Reporting, Audit.

Stack: Spring Boot, Spring Security, PostgreSQL (Neon, direct connection via a non-owner `app_user` role — see Data & Correctness Architecture), Flyway (schema + the raw-SQL exclusion constraint migration), JPA/Hibernate, REST APIs, Bean Validation, OpenAPI/Swagger, Docker. DDD/CQRS/Hexagonal patterns applied specifically to the Scheduling/Appointment bounded context, where the payoff is real (the domain logic is genuinely non-trivial there) — not forced onto simpler CRUD-shaped modules like Department management, where it would just be ceremony.

**Admin CRUD modules share a generic base, rather than four independent implementations.** Department, Specialty, AppointmentType, and Holiday management are structurally near-identical (list/create/update/soft-delete, admin-only) — writing each as its own controller/service/repository trio is real, avoidable duplication. One generic Spring Data JPA repository plus a thin generic service/controller base, with each concrete module overriding only what's actually different (validation rules, cascade behavior), cuts ~4x duplication to roughly ~1.3x. This does not apply to the Scheduling/Appointment/IAM modules, which have real, non-generic domain logic and get their own dedicated implementation.

**Reporting aggregates are single `GROUP BY` SQL queries, not application-side loops.** Doctor utilization, department load, and cancellation rate must each be one aggregate query against the database, not "load all doctors, then loop and count each doctor's appointments" — the latter is the classic Hibernate N+1 pattern and looks like perfectly natural code, which is exactly why it's worth stating explicitly as a design rule rather than trusting it to be caught at implementation time.

## Notifications

Channels: email (v1), SMS/push documented as future extension points — the notification system is abstracted (a `NotificationTemplate`/provider interface) specifically so a channel can be added later without touching booking logic. Events: booking confirmed, reminder (e.g. 24h and 2h before), cancellation, reschedule, hospital-side schedule change notice to affected patients.

**Sending is async via an outbox, not synchronous.** The booking endpoint never calls the email provider directly and waits — it writes a `NotificationOutbox` row (event type, recipient, payload) in the *same transaction* as the booking itself, then returns. A separate scheduled sender picks up pending outbox rows and sends them, with retry/backoff on provider failure. This means a slow or momentarily-down email provider never adds latency to the booking response, and a failed send is a retryable row in a table, not a silently swallowed exception nobody sees.

**The reminder job needs a distributed lock, not a plain `@Scheduled` poller.** Render/Railway can run more than one backend instance (during a deploy overlap, or under load) — two instances independently polling "appointments starting in the next N hours" will both claim and send the same reminder unless claiming is exclusive. Use `SELECT ... FOR UPDATE SKIP LOCKED` when the reminder job selects candidate rows (a Postgres-native pattern, no extra infrastructure needed) so only one instance ever wins a given row, then marks it sent.

## Security & Privacy

Treated as first-class, not an afterthought:

- HTTPS in production, secure password hashing, session/JWT security, RBAC, input validation, SQL injection/XSS/CSRF protection where applicable, rate limiting, secure HTTP headers, secrets outside source code, environment-based config, database backups, principle of least privilege
- Most important invariant: **a patient can only ever access their own appointment information; a doctor can only access information their role/assignment permits** — this is the same guarantee the RLS layer in Data & Correctness Architecture exists to enforce at the DB level, not just in application code
- Privacy: minimize collected data, encrypt sensitive fields where appropriate, never expose patient data in URLs, never log sensitive information, maintain audit trails, define retention/deletion policy
- **Bhutanese regulatory compliance is an open item, not an assumption.** The design should be built to accommodate applicable Bhutanese healthcare/privacy/government information-security requirements, but the exact legal requirements have not been verified in this session — treat this as a documented gap, not a hidden one. Given the scenario framing (Premise 3 — no real deployment, no real patient data), this doesn't block the portfolio build, but would need real verification before any real deployment.

## Decisions Resolved During Review

- **Timezone handling: store UTC, render Asia/Thimphu (UTC+6).** JDWNRH is in Bhutan; typical cloud infra defaults to UTC. All timestamps stored UTC; slot generation, display, and reminder timing convert to Asia/Thimphu at the presentation/notification layer, never at the storage layer.
- **Reminder trigger mechanism:** a scheduled job (Spring's `@Scheduled` or a platform-level cron, depending on deploy target) polls for appointments starting in the next N hours (e.g. 24h, 2h) and sends the reminder, marking the appointment as "reminded" per window to avoid duplicate sends.
- **Cancellation frees the slot immediately** — enforced structurally by the partial exclusion constraint (see Data & Correctness Architecture), not just by application logic remembering to update a flag.

## Observability

**Structured JSON logs with a request/correlation ID** threaded through every request via a servlet filter/interceptor. Booking failures (exclusion constraint violations), RLS denials, and notification outbox retries log at entry and on each significant branch with enough context (user id, doctor id, attempted appointment range, outcome) to reconstruct an incident from logs alone — this is deliberately specified now because "add logging later" is exactly the kind of thing that silently never happens once the walking skeleton is live.

## Success Criteria

- A patient can browse department → specialty → doctor → available slots (backend-computed) → book, and receives a confirmation + reminder(s) before the appointment
- Concurrent booking attempts on the same doctor-time range (including overlapping different-length appointments) never produce two active bookings — proven by a checked-in load test, connecting the same way the booking endpoint does in production (direct, non-pooled Postgres connection via the `app_user` role — required for the RLS `SET LOCAL` decision above). **The concurrency level is sized to what the deployed Neon tier's direct-connection limit actually supports, verified before the test is written, not assumed** — lower Neon tiers cap direct connections well below 100, so the test reports the maximum concurrency the real deployed tier supports (upgrading the tier if needed to hit a number worth reporting), rather than hard-coding "50-100" and treating connection exhaustion as test noise to explain away. Failures are still triaged by type (constraint violation = correct rejection; genuine connection error = infra issue to fix, not a correctness result) before being reported.
- All tests that touch the exclusion constraint, RLS, or partial indexes run against a **real Postgres via Testcontainers**, never an in-memory substitute (H2 cannot execute GiST exclusion constraints or RLS policies, so it would silently pass while the real constraint could still be broken) — including a dedicated Testcontainers + PgBouncer (transaction-mode) test lane that proves the RLS `SET LOCAL` mechanism actually breaks under pooling as expected, turning the design's biggest documented risk into an automated regression test rather than a one-time manual smoke check nothing re-runs
- Cancelling an appointment immediately frees its slot for rebooking — verified by a test, not just assumed from the constraint definition
- All seven roles have distinct, correctly-scoped access; enforced at both application (Spring Security) and database (RLS) layers
- Admin can view operational reporting (appointment volume, doctor utilization, cancellation rate, department load, no-show rate) from real seeded data, not hardcoded numbers
- Audit log captures every listed event with who/what/when/resource/before/after
- The whole system is live at a public URL, seeded with realistic (fictional) demo data, deployable from a fresh clone with documented setup steps

## Distribution Plan

Spring Boot doesn't run on Vercel's serverless function runtimes (Node.js/Python/Bun/Rust) — it needs a host that runs a long-lived JVM process or a Docker container. Recommend Railway or Render for the backend (both support Docker/Java with simple git-integrated deploys and a free/cheap tier), Neon Postgres as the hosted database (direct connection, not pooled — see Data & Correctness Architecture), and, once the frontend framework decision above is made, Vercel for a decoupled SPA frontend if one is used. CI is each platform's git-integrated deploy-on-push; no separate pipeline needed at this scale, but Flyway migrations should run as a deploy step, not manually.

**Free-tier cold-start risk:** Railway/Render free tiers idle out and cold-start (30-50s) after inactivity, which can make a portfolio demo look broken on first load if someone opens the link cold. Budget for a paid always-on tier before showing this to anyone, or add a lightweight keepalive ping — don't let a first impression get sunk by a JVM cold start.

**Neon tier must support the load test's concurrency claim.** Check the direct-connection limit on the actual Neon tier used before writing the concurrent-booking load test (see Success Criteria) — the load test is the design's central correctness artifact, so the number it reports has to reflect real deployed capacity, not an assumed one.
